# Changelog

All notable changes to Platehouse are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.1.0] - unreleased

### Added

- Slicing gate harness in tools/slicing-gate: picks the Task 1 sample from the .3mf metadata, flattens OrcaSlicer's BBL profiles, and slices every plate in a throwaway network-less container on Hades, with a report and Jon's pass rule ([#1](https://github.com/jonathanmcohen/platehouse/pull/1)).
- CI job for the slicing gate: on pull requests and pushes that touch tools/slicing-gate, it runs the gate tests on Node 26, builds the gate image so every build step and check runs on GitHub instead of first on Hades, and smoke-checks the built image with no network; nothing is pushed and no secret is used ([#7](https://github.com/jonathanmcohen/platehouse/pull/7)).
- pnpm workspace on Node 26.13.0 and pnpm 12.18.0, with TypeScript 7.0.2, Vitest 5.1.0 and Biome 2.6.6, every dependency pinned exactly; the slicing gate stays outside the workspace and outside Biome. The server's config loader reads every key of the configuration contract from the environment with zod, refuses to start when a value is missing or invalid, and names the key without ever printing its value; it builds absolute URLs from PUBLIC_ORIGIN only, defaults SLICE_PLATE_SECONDS to 120 from the gate's worst plate (55.31 s on Hades), and requires LINK_SECRET to be at least 32 bytes ([#14](https://github.com/jonathanmcohen/platehouse/pull/14)).
- CI for the workspace: every pull request and every push to main or a release branch now runs Biome, tsc -b, the unit tests and the integration tests, in that order, on the Node version in .node-version; each test job fails with "No tests ran" when no test actually ran (a test skipped by a filter does not count) and logs how many did. The slicing gate job still runs only when tools/slicing-gate, the workflow or .node-version changes, and now takes its Node version from .node-version (#16). The integration suite starts with a smoke test that brings up postgres:17-alpine and the pinned S3 test server through testcontainers, with shared helpers the database and storage tests will build on ([#17](https://github.com/jonathanmcohen/platehouse/pull/17)).
- 3MF parser in packages/threemf, a port of the Bambu Plates parser: it reads each plate's name, object count, thumbnail and Bambu's own slice numbers, the project's filament list, the printer and nozzle the file was sliced for, the process name and the start of the model file for the MakerWorld details. It reads entries only by their exact name, compared byte for byte, so a name with a backslash is never taken for the Bambu entry, and the name of an entry it does not read, such as one with '..' or an absolute path, never makes the file damaged. It keeps a plate number, from model_settings.config or a plate_N.png name, only when it is a whole number from 1 that JavaScript holds exactly, and refuses any XML with a DTD. A file over any Bambu Plates ceiling (5 MiB per config entry, 128 plates, 256 filaments, 128 MiB of thumbnails per file, which maxThumbnailBytes can lower), or one that is not a readable zip, comes back as "No Bambu plate data in this file" without throwing, and a print time over ten years counts as unsliced. A plate thumbnail over 10 MiB gives way to the plate's small thumbnail, and its bytes still count against the per-file budget. A broken model_settings.config falls back to the plate list from the thumbnail names, and a broken slice_info.config leaves the plates unsliced. Every ceiling counts bytes actually inflated. Thumbnails are checked against the ceilings first and then handed over one at a time in plate order, so a damaged file hands over none. A filesystem error reaches the caller as ReadUnavailable, and an error from the caller's thumbnail callback or from the parser's own code reaches the caller unchanged; neither is ever reported as damage ([#18](https://github.com/jonathanmcohen/platehouse/pull/18)).
- Object storage layer in apps/server/src/storage: every blob lives under models/<modelId>/<blobId>, two lowercase UUIDv7 ids with no user text or extension, and the store refuses to write or delete any other key; putBlob hashes the bytes with SHA-256 while it uploads (multipart for large files), then checks the stored size and deletes the object if it does not match; getBlobStream, deleteBlobs (safe to retry) and listPrefix complete the store, and nothing hands out a presigned URL. readVersioning reports the bucket's versioning as enabled, suspended, off or unknown for the settings page warning. An unreachable or timed-out store raises StoreUnavailable, a missing object BlobNotFound and a refusal StoreError, and none of them ever carries the secret access key ([#26](https://github.com/jonathanmcohen/platehouse/pull/26)).
- Database schema 0001 for Postgres 17, hand-written SQL with pg_trgm and trigram indexes on model names, captions, creators and tags; the schema itself refuses a bucket key other than models/<modelId>/<blobId>, a stored blob without its size and SHA-256, a finished estimate without a time and weight, a failed one without a reason, and a second settings row, and seeds the default printer, the P1S with a 0.4 mm nozzle. A forward-only migrator applies the numbered SQL files in one transaction under an advisory lock and refuses to run when an applied file was edited or removed. Repositories for models (create, get with or without trashed models, case-insensitive search over name, caption, creator and tag, trash, restore and the purge list), blobs, files, plates, estimates, tags, collections, API tokens, sessions and settings, with ids made as UUIDv7 in the app ([#27](https://github.com/jonathanmcohen/platehouse/pull/27)).
- Organising the library in apps/server/src/library: renaming a model or a file changes its display name only, never its bucket key or a file's original name; tags and collections are added and removed per model, a model can sit in several collections, and collections stay flat. Delete moves a model to the trash, where it is gone from the library, search and every lookup the API uses, and restore brings it back with its files, tags and collections. purgeExpired(now) purges models trashed more than 30 days before now, and finishes any purge that began and failed however recently the model was trashed, and emptyTrash purges the whole trash: a purge locks the model's row, reads its blob rows and lists its prefix, and only then marks it as purge started (schema 0002, committed just before the first delete, so a purge that fails before deleting anything, such as during a store outage, leaves no mark and the model can still be restored), then deletes its bucket objects (every blob, plus any other key under its prefix in the models/<modelId>/<blobId> layout), checks the prefix is empty and only then removes its rows; a purge that fails part way leaves the model in the trash and a later run finishes it. Apart from its own storage write check (checks/write-check), the app never deletes a key outside the blob layout, so such an object fails the purge with an error naming the first keys left, to be removed by hand. A model whose purge has begun deleting cannot be restored, and a restore made while its objects are being deleted is refused at once; any other trashed model is restored without reading the bucket, and an object it lost some other way shows as unavailable instead of blocking the restore. Search covers name, caption, creator and tag, ranked by trigram similarity across all four, with tag, collection and creator filters and an opaque cursor for the next page. The daily 03:30 schedule for purgeExpired is left to the job runner (Task 8) ([#35](https://github.com/jonathanmcohen/platehouse/pull/35)).
- MakerWorld details in packages/makerworld: reads the title, designer, description and licence from a .3mf's model XML, only when it names a Designer and never for the Gridfinity Layout Tool; converts the description from HTML to Markdown with its escaping re-derived for markdown-it instead of Kramdown, so designer text shows as written; maps the licence to its SPDX id (the CC 4.0 licences and CC0-1.0), or to a "License on MakerWorld" footer for the two MakerWorld licences; and renders Markdown for the web app with raw HTML off, links only to http(s) addresses, no images (an image in a description shows as a link, so no description can load a remote address; Jon's decision, 2026-11-08) and DOMPurify over the output. A crafted 256 KiB description converts in bounded time and size ([#24](https://github.com/jonathanmcohen/platehouse/pull/24)).
- Slicer container in apps/slicer, behind Slicer HTTP contract v1 (zod schemas in packages/slicer-contract): it slices one plate of a .3mf with OrcaSlicer 2.5.0 and returns its time, weight and grams per filament, renders a .scad to STL or PNG with OpenSCAD 2026.11-RC0, converts STEP to GLB with occt-import-js, and lists every Bambu printer and nozzle Orca ships a profile for (56) as the printer menu. It runs one heavy job at a time, a slice, a render or a STEP conversion, and answers 409 busy to a request for any of them while one runs, so callers retry, draining a body still arriving for up to 5 s before it closes the connection, so a client sending a large file reads the 409 rather than a reset; it sets its own request timeout, long enough for the largest upload plus the longest time cap, rather than Node's 300 s default; it kills a plate's whole process group at its time cap (SLICE_PLATE_SECONDS 120 from the slicing gate, plus 60 s), keeps the file's own process and loads only the printer's machine preset and a default filament per printer and type, and reports each refusal with Orca's own code and reason. An error in one request costs that request a 500, closed the same lingering way so a large upload reads it, or its connection, never the server process, and undoes its job: its program is killed, its folder deleted and the lock freed. A job folder that will not delete is logged and never changes an answer; job folders left behind are removed at start-up, after every job and by a health check that finds /work below the floor, and /v1/health answers 500 while no job runs and /work has less free space than WORK_MIN_FREE_MIB (default 640 MiB: the largest upload, 512 MiB, plus room for Orca's output), so Docker's health check sees a /work that leftovers have filled. OpenSCAD runs under landrun, which limits its write access to its own job folder; a self-test before the first render checks that the sandbox blocks a read outside the job folder, and renders are refused until that check passes. The image follows the slicing gate's proven build, runs as a non-root user on a read-only root with /work on tmpfs, runs tini as PID 1 to reap processes orphaned by a kill at the time cap, and has a health check. buildSliceable in packages/threemf generates a two-plate, two-filament cube project Orca slices, for the container tests and the coming update workflow. CI builds the image and runs the container tests when the slicer or anything its image is built from changes; nothing is published ([#36](https://github.com/jonathanmcohen/platehouse/pull/36)).
- Background jobs and the ingest pipeline in apps/server/src/jobs and apps/server/src/ingest. pg-boss 12.38.1 runs three queues in the app's own Postgres (schema pgboss): ingest, two files at a time and never retried, so a failed upload fails visibly; slicer, a singleton queue that runs one slice at a time, which Task 12 fills; and maintenance, where Task 14's purgeExpired now runs daily at 03:30 local time and an orphan sweep daily at 04:00, each once on start if the app was down at that hour. The orphan sweep lists the bucket a page at a time and deletes any object under models/ that has no blob row and is more than 24 hours old, such as one left by a process that died between an upload and its commit; a key outside the blob layout is left alone, a second run finds nothing more to do, and each run logs what it listed and deleted. Since the bucket is the only copy of the bytes, the sweep lists the whole prefix first and deletes nothing, logging why, when the blobs table holds no stored rows (a database that has lost its rows, a wrong DATABASE_URL or a second instance on the same bucket) or when a run would delete more than 10 objects or a tenth of those it listed, whichever is more, and never more than 100. ingestFile takes only .3mf, .stl, .step, .stp and .scad, and only when the first bytes agree with the name (a .3mf must be a zip, a .scad UTF-8 text, an .stl ASCII or a binary STL whose size matches its triangle count, or, when a writer left the count at 0 or wrong, whose size is its header and whole 50-byte facets and whose bytes are not text, a zip, a PNG or a JPEG, a .step or .stp must start with ISO-10303-21); anything else is refused with a message and nothing is stored. A file is uploaded and hashed first, a .3mf is then parsed with each plate thumbnail stored as it comes, and only then does one transaction write the model, the file, its filament list, its plates and Bambu's own numbers. Each file becomes its own model unless the batch is combined, and files of a combined batch that finish together still make one model. MakerWorld details fill only empty fields, so nothing Jon set is overwritten and a description already set is never edited. A MakerWorld-only licence ("License on MakerWorld: ...") is always stored as the model's licence note unless the model already has a note, whatever SPDX licence it has, and is added at the foot of the description only when the description and the licence are both empty; the model page will show the note (Task 20). A .3mf with no Bambu plate data is stored and marked as such. A failure at any step, a store outage included ("Storage is unavailable right now; nothing was saved"), deletes the objects already put and leaves no row. When the commit went through but its answer was lost (Postgres reports the transaction's own id as committed), the upload is stored and ingest reports it as stored, so a retry does not make a second copy; the objects are deleted when the transaction never got an id (the database was down at BEGIN, so nothing can have committed) or when Postgres reports that id as aborted, and when the database cannot say or the commit is still in flight, the objects are kept, the upload fails, and any left with no row are removed by the orphan sweep. Ingest never calls the slicer, so it returns before any slice runs ([#49](https://github.com/jonathanmcohen/platehouse/pull/49)).
- Bambu's own filament presets in the slicer (Jon, 2026-11-08: "I use mostly Bambu Filaments"): a slice now loads, for each filament, the printer's Bambu preset for its type where Orca 2.5.0 has one (PLA: Bambu PLA Basic, PETG: Bambu PETG HF, ABS: Bambu ABS, ASA: Bambu ASA, TPU: Bambu TPU 95A, kept in one table in apps/slicer/src/profiles.ts), else the printer's Generic preset, else the file's own filament. /v1/profiles lists that default once per printer and type, naming the printer, and a slice result's filamentProfiles names the preset loaded for each slot, or null where the file's own was kept. All 56 printers get Bambu's preset for all five types except 30 printer and type pairs Orca has no preset of either kind for (TPU on every 0.2 mm nozzle, ABS and ASA on the A1 mini and the A2L), which keep the file's own filament ([#55](https://github.com/jonathanmcohen/platehouse/pull/55)).
- Resumable uploads in apps/server/src/uploads: one tus 1.0.0 upload handler, mounted at /app/uploads for the UI behind its session and at /api/v1/uploads for the API behind a bearer token (registerTus takes each mount's auth hook, so a request the hook refuses stores nothing). An upload must give its size, at most 512 MiB, and its file name, and may name an existing model or a batch to combine; a missing name is refused with 400, an oversized or open-ended upload with 413 or 400, and a file type Platehouse does not take with 415, before any byte is sent. A client may send the file in chunks and resume after a dropped connection from where the server stopped, or send it all in one PATCH as curl does. Partial uploads live in TMP_DIR/uploads; a finished upload is queued for ingest under its own id, GET <prefix>/<id>/result reports pending, done (with the model and file) or failed (with ingest's own plain message, or, when the outcome cannot be confirmed, a note to check the library before sending the file again; never an internal error). The temp file is deleted after ingest whether it succeeds or fails, and the upload's small info file is kept, with a record of what the ingest did, until the sweep removes it a day later. During that day HEAD on the upload answers from that record, under the same lock tus uses, so it cannot catch the clean-up half done: after an ingest that stored the file, or one whose commit the database could not confirm, it answers finished (Upload-Offset equal to Upload-Length), so a client that retries after losing the last answer, or sends the same file again with its resume fingerprint kept, sends nothing and makes no second model; after an ingest that failed with nothing saved, it answers 410, so the same client starts a fresh upload. Nothing saved includes a database that was down when ingest started, and a failure while ingest was still writing its rows (a Postgres restart mid-insert, say), even when the database cannot then be asked how the transaction ended: no COMMIT was sent, so the stored objects are deleted. Only a failure at COMMIT whose outcome the database cannot report keeps them and counts as unconfirmed. HEAD carries no target, so the web client (Task 19) must put the target model or batch into its resume fingerprint, or drop the fingerprint once an upload succeeds; with tus-js-client's default settings, the same file dropped on another model within a day would resume the stored upload and store nothing there. An upload left untouched for 24 hours is deleted by an hourly sweep on the maintenance queue and never becomes a model. When tus answers a PATCH before reading its body (a wrong offset, too large), the answer goes out at once with Connection: close and the rest of the body is read off for up to 5 s before the connection closes, so a client still sending reads the answer rather than a reset. Responses carry no CORS headers and a relative Location, so no URL is taken from the request's Host header, and there is no DELETE on an upload ([#61](https://github.com/jonathanmcohen/platehouse/pull/61)).
- Plate estimates and the printer setting in apps/server/src/estimates. The printer menu is the slicer's /v1/profiles printer list, read once per Orca version, and the selected printer defaults to the P1S with a 0.4 mm nozzle. Every plate of a live .3mf gets numbers: Bambu's own from the file, labelled with the printer it was sliced for, and, when the file has none for the selected printer, an OrcaSlicer estimate for that printer, sliced in the background one plate at a time on the slicer queue after the upload has returned. A slice the slicer refuses shows its reason in plain words, with Orca's own message kept for a Details toggle, while the other plates still get their numbers, and it can be retried from the stored file. A 409 busy or a lost connection is retried three times with backoff from 10 s, and then the plate fails with "The slicer could not slice this plate.", so a slicer restart never leaves a plate estimating forever. A slicer that takes no connection at all (stopped or restarting, so it never saw the plate), or a store the file cannot be read from, uses up no retry: the slice waits for it to answer, holding the queue so the plates behind it wait too, and goes back on the queue if it is still down after 30 s. A plate that cannot reach the slicer or the store for about 2 minutes (three trips back on the queue) then shows as failed, and the next Orca poll, every 10 minutes, queues it again once they answer. A plate whose slice was lost mid-way is not queued again automatically, since it may be what stopped the slicer; the retry button still queues it. Changing the printer cancels the queued slices for the old printer and re-estimates the library; until a plate's new estimate lands, its old one stays visible, marked as made for the previous printer. The Orca-version poll runs at start-up and every 10 minutes: a new Orca version re-estimates every live plate, and every estimate records the Orca version that made it. Each poll also fails a slice whose job was lost, queues again a waiting estimate whose job was lost, and queues any plate still without an estimate. Schema 0003 stores, for each filament of an estimate, the preset that produced its grams and whether it was Bambu's own, Generic or the file's own filament, so the plate can say which preset it used ([#62](https://github.com/jonathanmcohen/platehouse/pull/62)).
- Inbox watcher in apps/server/src/inbox/watch.ts: a file placed in the inbox folder (INBOX_DIR) becomes a model of its own with no manual step. The folder is polled every 5 seconds rather than watched for events, which bind mounts and network copies drop, and a file is imported only once its size and modification time have stayed the same across polls for INBOX_SETTLE_SECONDS (15 by default), counted from when the watcher first saw them, read for each file as it is looked at so a slow import earlier in the same poll does not shorten the next file's wait, so a copy still running, or one that kept its source's old timestamp, is not taken early. Dotfiles, names ending in .part, .crdownload or .tmp, folders and symlinks are left alone. A settled file is opened once, without following a symlink, and the open file must still be the regular file that settled (the same device, inode, size and modification time), so a symlink renamed over it after the folder was listed is never read; everything after reads that open file, never the inbox path: its hash, and a copy in TMP_DIR/inbox-copies that ingest reads and that is deleted once ingest is done with it. The copy holds no more than the size that settled, so bytes appended later never reach it and what is stored is never larger than the size the limit was checked against; a file that grew, shrank or was written to after it settled is not imported on that pass and takes no strike, and is imported as it then is once it settles again. After ingest stores the file, the watcher runs onIngested with it, a required dependency so a server that leaves it out fails to compile, as the ingest queue's worker does, so an inbox file's plates are queued for estimates as soon as it is stored rather than waiting for the 10-minute Orca poll; it runs too for an earlier attempt's import found after its answer was lost, and a failure there is logged, never thrown, since the file is stored. The watcher then checks that the recorded size and SHA-256 match the inbox copy, and that its name still holds that same file, and only then deletes it; a symlink found under the name by then is left alone, and so is a new file put under the name while the import ran, which was never imported: it stays in the inbox untouched and is imported later as a model of its own, and the import that finished stands. The delete never goes by name, which would act on whatever the name holds at that moment (rsync renames a new file over a name): the file under the name is first moved into a hidden holding folder of its own inside the inbox, and deleted there only if it is the very file that was imported and its size and modification time are still those that settled; one written over in place since it was checked (as Windows Explorer, or cp onto an existing name, does) holds bytes that were never imported, so it goes to inbox/failed with a reason saying a model was made, instead of being deleted. A file put under the name in the meantime is put back and imported as a new file. Putting it back never replaces a file that took the name since: it is hard-linked back, or, where a hard link to it is refused (a file another user owns, such as one written over SMB), copied whole into a file of the watcher's own in the holding folder and only then hard-linked under the name, so a part-written copy never appears there, even when the disk fills during the copy. If the file's size or modification time moved during the copy, its writer still has it open, so the copy would be cut short: it is not left under the name, and the file itself, which the writer goes on writing, goes to inbox/failed with a reason saying it was still being written. On a filesystem with no hard links at all, or when putting it back fails for another reason such as a full disk or a file it cannot read, it is not put back and goes to inbox/failed with a reason saying it could not be put back under its name. If another file took the name first, it goes to inbox/failed with a reason saying it was not imported. A holding folder left by a crash in that moment is emptied into inbox/failed, with a reason, when the watcher next starts, and a copy that was being put back is deleted there rather than kept. A file goes to inbox/failed at once only for a reason that belongs to the file: ingest refuses it for its type or content (unsupported_type) or its target model (model_not_found), it is larger than the upload limit (MAX_UPLOAD_BYTES from the tus uploads, 512 MiB, read from its size before anything is uploaded; the reason gives the limit in bytes and in MiB, both worked out from it), or its name is not valid UTF-8. It moves there as "name (2).ext" and so on when the name is taken and shortened when it would not fit, with name.reason.txt beside it holding one plain sentence. If inbox/failed is a symlink or anything else that is not a real folder, nothing is moved through it: each file that would have been is logged and stays in the inbox, except an imported file that changed, could not be confirmed, or could not be checked or deleted in its holding folder, which stays out of the inbox in that hidden holding folder, logged, and the restart sweep moves it to inbox/failed with its reason once inbox/failed is usable; a file that itself changed during its import, or whose stored copy could not be confirmed, goes there too, through the same holding folder and only if it is the very file that was imported, with a reason saying a model was made. A damaged .3mf is not a failure: ingest stores it as a model with no plate data. Any other error leaves the file in place and stops the pass: ingest's ingest_failed (the save failed for a reason that is not the file's, such as a database or filesystem fault), storage_unavailable, a commit whose outcome is not known, and anything from the store, the database or elsewhere. The watcher then runs one quick check of the environment, each part given 5 seconds: a database query that also fails when the database is read-only or the role may not read or insert into files, then a model, a pending blob and a file row written in a transaction that is rolled back; a bucket listing, then a small object put and deleted under a key outside models/, so the orphan sweep never sees it; and a small file written, flushed and deleted in TMP_DIR/inbox-copies, where the copy ingest reads goes. A copy that cannot be written there (TMP_DIR full, read-only, unwritable or gone) never counts against the file: it is an outage even when the checks pass, the next try coming 5 seconds later and doubling to 5 minutes while copies still fail, and a failure reading the inbox file itself is handled like any other error. If a check fails it is an outage: it is logged once when it starts, with the error, and once when it ends, and no file is tried, so none is uploaded again, until a check passes. The checks back off, 5 seconds after the first and doubling after each failed check up to 5 minutes, and start again at 5 seconds after a good pass. If all the checks pass, the error counts against that file, and after 3 such failures in a row while the file is unchanged it moves to failed with a reason quoting the error and its cause, at the end of that pass and only if its name still holds that same file, so a corrected copy or a symlink dropped in under the name meanwhile is not moved there under the old file's reason (an ingest refusal is moved under the same check); a change to the file starts its count again, and the other files keep importing in between. But when a second file fails the same way in the same pass with the checks passing (the same error code inside ingest's wrapper, or the same error name), the fault is taken to be one the checks cannot see, not the files': neither failure counts, the inbox is held, and the next try comes 5 seconds later, doubling to 5 minutes. Once the wait has reached 5 minutes (about 10 minutes of held tries), each try counts again, so two files that are each bad the same way still reach failed after 3 more tries 5 minutes apart. The hold is logged when it starts, when its tries start to count and when it ends, and it ends, and is forgotten, after any pass that leaves no hold armed, including one with no held file left to try, so a later fault always starts a hold of its own. The checks' writes are small and rolled back or deleted, so a fault can still miss them (a full Postgres disk fails an insert only when the table file has to grow, and a rolled-back write is not flushed); such a fault, one with a single file in the inbox, or one meeting files that settle apart, still moves the files it meets to failed after their tries. The watcher chooses each import's file row id itself and passes it to ingest, which gains an optional fileId for it: the id is shaped like a UUIDv7 and derived from the file's name, size, SHA-256 and the time it reached the inbox, so the same copy gets the same id after a restart. Before every import, not only after an outage, the watcher asks the files repository (files.findImported), in one query, for the rows under every id this copy can have (attempts 0 to 99). A live row under any of them means an earlier attempt's commit landed and only its answer was lost, in this process or in one before a restart, so the file is not imported a second time and its inbox copy is checked and deleted as after any import. Only an inbox attempt for this copy can write those ids, so an upload of the same name and bytes through the web UI or the API, which gets a random id, never stands in for the inbox copy, and an import of the same file made before this copy reached the inbox does not count either. A row whose model is in the trash or being purged (a purge deletes its stored bytes) does not count; with no live row, the copy is imported under the lowest id that has no row. Every id is asked about, not only those up to the first with no row, because a purge can delete an earlier attempt's row after a later attempt committed with its answer lost. The arrival time is the file's ctime, taken when the watcher first sees its current size, modification time and inode and kept while they stay the same, so a chmod or an xattr write does not move it. The kept ctime lasts only as long as the process, so a metadata change made after a lost answer and before a restart can still let the file be imported twice. The lookup comes before the upload, so a database that cannot answer it stops the file before anything reaches the bucket. No file is retried in a loop: one that cannot be moved to failed, or whose inbox copy cannot be moved into its holding folder after its import, stays put, is logged, and is not tried again until it changes. One whose check or delete inside the holding folder fails is never put back under its name: it goes to inbox/failed with the reason it already had; else, when only the delete failed after it was shown to be the imported file, with one saying it was stored but could not be removed from the inbox, so the model may already be in the library; and when the check itself failed, so it may be a newer file put under the name just before it was held, with one saying Platehouse could not check whether it is the imported file or a newer one, so compare it with the model before deleting it; or it stays in the holding folder for the restart sweep while inbox/failed is unusable. The blob store gains checkWrite, which puts and deletes one fixed object, checks/write-check, outside the blob layout; it is the only key outside models/ the app writes or deletes. On a bucket with versioning on it deletes the exact version it wrote, so the checks leave no old versions or delete markers behind for the retention period; a key that may not delete a version (s3:DeleteObjectVersion), or a provider that refuses it, gets a plain delete instead, which leaves the check's version and a delete marker until the retention period ends. The server built in [#105](https://github.com/jonathanmcohen/platehouse/pull/105) starts the watcher and stops it, passing TMP_DIR as tmpDir, the ingest service as ingest, (id) => files.get(id) as storedFile, (q) => files.findImported(q) as findImported, (r) => estimates.enqueueFile(r.fileId) as onIngested (enqueueFile takes the file id, not the ingest result, so it cannot be passed bare) and inboxProbes({ db, store, tmpDir }), with the same TMP_DIR, as probes ([#59](https://github.com/jonathanmcohen/platehouse/pull/59)).
- OpenSCAD renders and STEP meshes in apps/server/src/derived: once a .scad or STEP file's row commits, ingest queues a job on the slicer queue (ingest itself never calls the slicer), and the job sends the file to the slicer container, which renders a .scad to an STL and a PNG preview with OpenSCAD and converts a .step or .stp file to a GLB mesh, the only thing a browser will load for STEP. The results are stored as new blobs. When the slicer is busy or the connection drops, the job is retried by pg-boss itself, up to 3 times with backoff (the slicer queue's shared retry settings, which Task 12's slice jobs use too), and then the file shows "The slicer could not render this file." instead of waiting forever. A slicer that takes no connection at all (stopped or restarting), or that says OpenSCAD renders are off because its sandbox self-test failed, uses no retry and records nothing against the file: the job waits for it, asking again after a wait that doubles up to 15 minutes, keeping the retries it had left, and a replacement keeps the previous version until it renders. That wait lasts at most 2 hours from the first refusal, a deadline the job carries with it so a restart does not reset it; after that the file shows "The slicer is not answering. The render will need to be started again.", or for a replacement "The slicer is not answering, so the replacement was not saved. It will need to be sent again." and the replacement's new source is deleted. A storage outage, when the file cannot be read from the bucket or its renders cannot be saved there, is handled the same way: it uses no retry and is never blamed on the slicer, the job waits for the store on the same schedule and the same 2-hour limit, and after that the file shows "Storage is not answering. The render will need to be started again.", or for a replacement "Storage is not answering, so the replacement was not saved. It will need to be sent again." A store that answers but refuses (an HTTP 500, access denied, a missing bucket), or a source file that is missing from the bucket, is not blamed on the slicer either: the file shows "Storage refused this file, so the render could not finish.", or for a replacement "Storage refused the replacement, so it was not saved." and the replacement's new source is deleted; a 500 or similar server error, or a store that is throttling or timed out the request, is retried by pg-boss first, while access denied, a missing bucket or a missing file ends the render at once, since a retry cannot change it. A render error keeps the uploaded source and stores OpenSCAD's own message, or the STEP converter's, word for word, as text to show and never as HTML; a .scad over the slicer's 1 MiB limit or a STEP file over 256 MiB is refused with a message and never sent. Replacing a .scad or STEP file refuses a replacement over those limits before storing anything; otherwise it stores the new source beside the old one and renders it; only once the new renders are stored does the file switch over, and only then are the old source and renders deleted, so a failure part way, such as the slicer going away mid-render, leaves the previous version whole and says so. A replacement that OpenSCAD or the STEP converter rejects itself, such as a .scad that fails only inside the slicer's sandbox, is different, since it is the file that was uploaded: it becomes the file's source as uploaded and only the old source is deleted, while the previous STL and preview, or mesh, stay attached and are still served until a later render succeeds, which replaces and deletes them. The file then shows the program's own message after "OpenSCAD rejected the current version of this file, so the STL and preview shown are from an earlier version. OpenSCAD said:" (or "The STEP converter rejected the current version of this file, so the mesh shown is from an earlier version. The converter said:"), and the page can tell the kept renders belong to the previous version from their rows: each render's row is stamped with the creation time of the source it was rendered from, so a render whose stamp is older than the file's source row is from an earlier version, even when a render of the old source finished after the replacement was sent; no schema change was needed. A slicer that stays down, storage that stays down or refuses, or a slicer error still keeps the previous version and deletes the replacement, which then has to be sent again. A render check, a maintenance job meant to run every 15 minutes once its schedule is registered, repairs what a failure part way leaves behind, acting only on files at least 30 minutes old and never on one a queued or running job still owns: a .scad or STEP file that a database failure right after its upload left with no render job is queued; a file whose render job died before recording an outcome is marked "The render did not finish." and is not queued again, so a file that crashes the slicer cannot loop; and the new source a replacement left behind that way is deleted, object first, then its row ([#60](https://github.com/jonathanmcohen/platehouse/pull/60)).
- The server process in apps/server/src/main.ts and the app in apps/server/src/app.ts, so Platehouse now actually starts. Started with the configuration from the environment, it migrates the database, starts pg-boss and works every queue: ingest, the slicer queue (one worker that hands each job to estimates' slices or the OpenSCAD and STEP renders by its kind) and maintenance, where the trash purge runs daily at 03:30, the orphan sweep at 04:00, the stale-upload sweep hourly, the Orca-version poll every 10 minutes and once at startup, and the render check every 15 minutes, now scheduled. A file's plates are queued for estimates as soon as it is stored, whether it came through an upload or the inbox, and a .scad or STEP file queues its render once its row commits either way. The inbox watcher starts with the server and stops with it. GET /healthz answers 200 only when the database answers within 3 seconds and the job queues are running, and 503 otherwise, with no error detail in the body. The upload handler is mounted at /app/uploads and /api/v1/uploads, and this change refused every request there with 401; since [#109](https://github.com/jonathanmcohen/platehouse/pull/109), /app/uploads takes uploads from a signed-in browser, and /api/v1/uploads stays refused until API tokens are built (Task 16). The request timeout lets a whole 512 MiB upload through as one request at 1 Mbit/s. SIGTERM or SIGINT stops new requests (those in flight get 5 seconds), then the inbox watcher, then pg-boss (running jobs get 10 seconds to finish, then pg-boss marks them failed), then the database, and the process exits; if that takes more than 30 seconds it exits anyway, and a second signal exits at once ([#105](https://github.com/jonathanmcohen/platehouse/pull/105)).
- Login with Pocket ID, sessions and the route-class gate in apps/server/src/auth. GET /auth/login sends the browser to Pocket ID with the authorization code flow, PKCE S256, a state and a nonce, and the scopes openid email profile groups; the verifier, state and nonce wait in a signed, HttpOnly, 10-minute __Host-ph_login_<state> cookie, signed with a key derived from LINK_SECRET, one per login so two tabs that log in at once both finish. The redirect_uri, in the login and in the token exchange, is built from PUBLIC_ORIGIN, never from the Host or forwarded headers. GET /auth/callback lets a user in only when Pocket ID says they are in the OIDC_GROUP group (platehouse) and email_verified is true or the string "true", reading those from userinfo if the ID token leaves them out, and otherwise shows a plain page saying why. A session lasts 7 days without a request and 30 days at most, behind a __Host-ph_session cookie that is Secure, HttpOnly and SameSite=Lax; the sessions table stores only the SHA-256 of the cookie value, so a stored id is not a working cookie, and a daily maintenance task at 04:35 deletes sessions past either expiry. POST /auth/logout ends it, and only with Origin equal to PUBLIC_ORIGIN, so another site cannot sign you out; when the session store fails it answers 503 and keeps the session cookie, since the session it names is still live. The request log records each path without its query, so the login code never reaches the log. Pocket ID is asked nothing until the first login, so the server starts and keeps serving while it is down, and /auth/login then answers 503 "Login is unavailable right now". Every route has a class from the contract's table, and anything unlisted needs a session: a page without one is sent to the login, anything else gets 401, and the gate looks at the route a request matched, so it cannot read a path differently from the router. Every state-changing request (anything but GET, HEAD and OPTIONS) to a session route, the uploads at /app/uploads and any route added later included, needs Origin to equal PUBLIC_ORIGIN, or gets 403. /app/uploads now takes uploads from a signed-in browser; /api/v1/uploads still refuses everything until API tokens arrive. An answer given before a request's body is read (a refusal, a 404 with any content type, /healthz with a trickled body, Fastify's own 400 for a bad URL and 414 for an over-long parameter) now always carries Connection: close and closes within 5 seconds, because the root app no longer parses bodies and one hook releases them for every answer ([#109](https://github.com/jonathanmcohen/platehouse/pull/109); fixes [#107](https://github.com/jonathanmcohen/platehouse/issues/107) and [#108](https://github.com/jonathanmcohen/platehouse/issues/108)).
- Per-client API tokens and the public API in apps/server/src/api. Each client, such as Claude Code on one Mac, gets its own token from createToken, which Task 21's settings page will call: ph_ followed by 43 random characters, shown once and never stored, since api_tokens keeps only its SHA-256 and its first 8 characters; revokeToken ends one token and leaves the others working, and each token's last use is recorded. Every route under /api/v1, the uploads included, takes only Authorization: Bearer <token>: a session cookie or a token sent as a cookie never counts, nothing is sent to the login page and no Origin is needed, so scripts work; a missing, malformed, unknown or revoked token is 401 JSON, an unknown path under /api/v1 included, and API tokens keep working while Pocket ID is down. The API searches the library (by words, tag, collection, creator or externalRef, a page at a time), makes a model with its metadata, tags, collections and externalRef for the Manyfold importer (a taken externalRef is 409 and says whether that model is in the trash), reads a model with its files, plates and plate numbers, reads a file and streams its bytes, adds and removes tags and collection memberships, and uploads files as a new model or into an existing one with the same tus upload the UI uses. It has no route that deletes, trashes or purges anything, and a model in the trash is invisible to it: reading it is 404 and an upload into it is refused with 404 before any byte is stored. GET /api/v1/openapi.json describes every API route, generated from the routes themselves with @fastify/swagger 9.9.3, with its server URL built from PUBLIC_ORIGIN, never from the request. No CORS headers are sent, a preflight included. The request log now records request headers, with Authorization, Cookie and Proxy-Authorization redacted and Upload-Metadata cut to its key names, so no token, cookie or uploaded file name reaches the log. A HEAD on a file's content sends the file's headers and no bytes, after asking the store whether the object is there, so it answers 503 wherever the GET for the same file would: when the store is down or the object is gone from the bucket. Every API answer carries Cache-Control: no-store, the uploads and the 404 for an unknown path included, so no browser or proxy keeps a copy ([#116](https://github.com/jonathanmcohen/platehouse/pull/116)).
