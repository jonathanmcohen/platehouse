# Changelog

All notable changes to Platehouse are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.1.0] - unreleased

### Added

- Slicing gate harness in tools/slicing-gate: picks the Task 1 sample from the .3mf metadata, flattens OrcaSlicer's BBL profiles, and slices every plate in a throwaway network-less container on Hades, with a report and Jon's pass rule ([#1](https://github.com/jonathanmcohen/platehouse/pull/1)).
- CI job for the slicing gate: on pull requests and pushes that touch tools/slicing-gate, it runs the gate tests on Node 26, builds the gate image so every build step and check runs on GitHub instead of first on Hades, and smoke-checks the built image with no network; nothing is pushed and no secret is used ([#7](https://github.com/jonathanmcohen/platehouse/pull/7)).
- pnpm workspace on Node 26.13.0 and pnpm 12.18.0, with TypeScript 7.0.2, Vitest 5.1.0 and Biome 2.6.6, every dependency pinned exactly; the slicing gate stays outside the workspace and outside Biome. The server's config loader reads every key of the configuration contract from the environment with zod, refuses to start when a value is missing or invalid, and names the key without ever printing its value; it builds absolute URLs from PUBLIC_ORIGIN only, defaults SLICE_PLATE_SECONDS to 120 from the gate's worst plate (55.31 s on Hades), and requires LINK_SECRET to be at least 32 bytes ([#14](https://github.com/jonathanmcohen/platehouse/pull/14)).
- CI for the workspace: every pull request and every push to main or a release branch now runs Biome, tsc -b, the unit tests and the integration tests, in that order, on the Node version in .node-version; each test job fails with "No tests ran" when no test actually ran (a test skipped by a filter does not count) and logs how many did. The slicing gate job still runs only when tools/slicing-gate, the workflow or .node-version changes, and now takes its Node version from .node-version (#16). The integration suite starts with a smoke test that brings up postgres:17-alpine and the pinned S3 test server through testcontainers, with shared helpers the database and storage tests will build on ([#17](https://github.com/jonathanmcohen/platehouse/pull/17)).
- 3MF parser in packages/threemf, a port of the Bambu Plates parser: it reads each plate's name, object count, thumbnail and Bambu's own slice numbers, the project's filament list, the printer and nozzle the file was sliced for, the process name and the start of the model file for the MakerWorld details. It reads entries only by their exact name, compared byte for byte, so a name with a backslash is never taken for the Bambu entry, and the name of an entry it does not read, such as one with '..' or an absolute path, never makes the file damaged. It keeps a plate number, from model_settings.config or a plate_N.png name, only when it is a whole number from 1 that JavaScript holds exactly, and refuses any XML with a DTD. A file over any Bambu Plates ceiling (5 MiB per config entry, 128 plates, 256 filaments, 128 MiB of thumbnails per file, which maxThumbnailBytes can lower), or one that is not a readable zip, comes back as "No Bambu plate data in this file" without throwing, and a print time over ten years counts as unsliced. A plate thumbnail over 10 MiB gives way to the plate's small thumbnail, and its bytes still count against the per-file budget. A broken model_settings.config falls back to the plate list from the thumbnail names, and a broken slice_info.config leaves the plates unsliced. Every ceiling counts bytes actually inflated. Thumbnails are checked against the ceilings first and then handed over one at a time in plate order, so a damaged file hands over none. A filesystem error reaches the caller as ReadUnavailable, and an error from the caller's thumbnail callback or from the parser's own code reaches the caller unchanged; neither is ever reported as damage ([#18](https://github.com/jonathanmcohen/platehouse/pull/18)).
- Object storage layer in apps/server/src/storage: every blob lives under models/<modelId>/<blobId>, two lowercase UUIDv7 ids with no user text or extension, and the store refuses to write or delete any other key; putBlob hashes the bytes with SHA-256 while it uploads (multipart for large files), then checks the stored size and deletes the object if it does not match; getBlobStream, deleteBlobs (safe to retry) and listPrefix complete the store, and nothing hands out a presigned URL. readVersioning reports the bucket's versioning as enabled, suspended, off or unknown for the settings page warning. An unreachable or timed-out store raises StoreUnavailable, a missing object BlobNotFound and a refusal StoreError, and none of them ever carries the secret access key ([#26](https://github.com/jonathanmcohen/platehouse/pull/26)).
- Database schema 0001 for Postgres 17, hand-written SQL with pg_trgm and trigram indexes on model names, captions, creators and tags; the schema itself refuses a bucket key other than models/<modelId>/<blobId>, a stored blob without its size and SHA-256, a finished estimate without a time and weight, a failed one without a reason, and a second settings row, and seeds the default printer, the P1S with a 0.4 mm nozzle. A forward-only migrator applies the numbered SQL files in one transaction under an advisory lock and refuses to run when an applied file was edited or removed. Repositories for models (create, get with or without trashed models, case-insensitive search over name, caption, creator and tag, trash, restore and the purge list), blobs, files, plates, estimates, tags, collections, API tokens, sessions and settings, with ids made as UUIDv7 in the app ([#27](https://github.com/jonathanmcohen/platehouse/pull/27)).
- Organising the library in apps/server/src/library: renaming a model or a file changes its display name only, never its bucket key or a file's original name; tags and collections are added and removed per model, a model can sit in several collections, and collections stay flat. Delete moves a model to the trash, where it is gone from the library, search and every lookup the API uses, and restore brings it back with its files, tags and collections. purgeExpired(now) purges models trashed more than 30 days before now, and finishes any purge that began and failed however recently the model was trashed, and emptyTrash purges the whole trash: a purge locks the model's row, reads its blob rows and lists its prefix, and only then marks it as purge started (schema 0002, committed just before the first delete, so a purge that fails before deleting anything, such as during a store outage, leaves no mark and the model can still be restored), then deletes its bucket objects (every blob, plus any other key under its prefix in the models/<modelId>/<blobId> layout), checks the prefix is empty and only then removes its rows; a purge that fails part way leaves the model in the trash and a later run finishes it. The app never deletes a key outside the blob layout, so such an object fails the purge with an error naming the first keys left, to be removed by hand. A model whose purge has begun deleting cannot be restored, and a restore made while its objects are being deleted is refused at once; any other trashed model is restored without reading the bucket, and an object it lost some other way shows as unavailable instead of blocking the restore. Search covers name, caption, creator and tag, ranked by trigram similarity across all four, with tag, collection and creator filters and an opaque cursor for the next page. The daily 03:30 schedule for purgeExpired is left to the job runner (Task 8) ([#35](https://github.com/jonathanmcohen/platehouse/pull/35)).
- MakerWorld details in packages/makerworld: reads the title, designer, description and licence from a .3mf's model XML, only when it names a Designer and never for the Gridfinity Layout Tool; converts the description from HTML to Markdown with its escaping re-derived for markdown-it instead of Kramdown, so designer text shows as written; maps the licence to its CC 4.0 SPDX id, or to a "License on MakerWorld" footer for the two MakerWorld licences; and renders Markdown for the web app with raw HTML off, links only to http(s) addresses, no images (an image in a description shows as a link, so no description can load a remote address; Jon's decision, 2026-11-08) and DOMPurify over the output. A crafted 256 KiB description converts in bounded time and size ([#24](https://github.com/jonathanmcohen/platehouse/pull/24)).
- Slicer container in apps/slicer, behind Slicer HTTP contract v1 (zod schemas in packages/slicer-contract): it slices one plate of a .3mf with OrcaSlicer 2.5.0 and returns its time, weight and grams per filament, renders a .scad to STL or PNG with OpenSCAD 2026.11-RC0, converts STEP to GLB with occt-import-js, and lists every Bambu printer and nozzle Orca ships a profile for (56) as the printer menu. It runs one heavy job at a time, a slice, a render or a STEP conversion, and answers 409 busy to a request for any of them while one runs, so callers retry, draining a body still arriving for up to 5 s before it closes the connection, so a client sending a large file reads the 409 rather than a reset; it sets its own request timeout, long enough for the largest upload plus the longest time cap, rather than Node's 300 s default; it kills a plate's whole process group at its time cap (SLICE_PLATE_SECONDS 120 from the slicing gate, plus 60 s), keeps the file's own process and loads only the printer's machine preset and a generic filament per type, and reports each refusal with Orca's own code and reason. An error in one request costs that request a 500, closed the same lingering way so a large upload reads it, or its connection, never the server process, and undoes its job: its program is killed, its folder deleted and the lock freed. A job folder that will not delete is logged and never changes an answer; job folders left behind are removed at start-up, after every job and by a health check that finds /work below the floor, and /v1/health answers 500 while no job runs and /work has less free space than WORK_MIN_FREE_MIB (default 640 MiB: the largest upload, 512 MiB, plus room for Orca's output), so Docker's health check sees a /work that leftovers have filled. OpenSCAD runs under landrun, which limits its write access to its own job folder; a self-test before the first render checks that the sandbox blocks a read outside the job folder, and renders are refused until that check passes. The image follows the slicing gate's proven build, runs as a non-root user on a read-only root with /work on tmpfs, runs tini as PID 1 to reap processes orphaned by a kill at the time cap, and has a health check. buildSliceable in packages/threemf generates a two-plate, two-filament cube project Orca slices, for the container tests and the coming update workflow. CI builds the image and runs the container tests when the slicer or anything its image is built from changes; nothing is published ([#36](https://github.com/jonathanmcohen/platehouse/pull/36)).
- Background jobs and the ingest pipeline in apps/server/src/jobs and apps/server/src/ingest. pg-boss 12.38.1 runs three queues in the app's own Postgres (schema pgboss): ingest, two files at a time and never retried, so a failed upload fails visibly; slicer, a singleton queue that runs one slice at a time, which Task 12 fills; and maintenance, where Task 14's purgeExpired now runs daily at 03:30 local time and an orphan sweep daily at 04:00, each once on start if the app was down at that hour. The orphan sweep lists the bucket a page at a time and deletes any object under models/ that has no blob row and is more than 24 hours old, such as one left by a process that died between an upload and its commit; a key outside the blob layout is left alone, a second run finds nothing more to do, and each run logs what it listed and deleted. Since the bucket is the only copy of the bytes, the sweep lists the whole prefix first and deletes nothing, logging why, when the blobs table holds no stored rows (a database that has lost its rows, a wrong DATABASE_URL or a second instance on the same bucket) or when a run would delete more than 10 objects or a tenth of those it listed, whichever is more, and never more than 100. ingestFile takes only .3mf, .stl, .step, .stp and .scad, and only when the first bytes agree with the name (a .3mf must be a zip, a .scad UTF-8 text, an .stl ASCII or a binary STL whose size matches its triangle count, or, when a writer left the count at 0 or wrong, whose size is its header and whole 50-byte facets and whose bytes are not text, a zip, a PNG or a JPEG, a .step or .stp must start with ISO-10303-21); anything else is refused with a message and nothing is stored. A file is uploaded and hashed first, a .3mf is then parsed with each plate thumbnail stored as it comes, and only then does one transaction write the model, the file, its filament list, its plates and Bambu's own numbers. Each file becomes its own model unless the batch is combined, and files of a combined batch that finish together still make one model. MakerWorld details fill only empty fields, so nothing Jon set is overwritten and a description already set is never edited. A MakerWorld-only licence ("License on MakerWorld: ...") is always stored as the model's licence note unless the model already has a note, whatever SPDX licence it has, and is added at the foot of the description only when the description and the licence are both empty; the model page will show the note (Task 20). A .3mf with no Bambu plate data is stored and marked as such. A failure at any step, a store outage included ("Storage is unavailable right now; nothing was saved"), deletes the objects already put and leaves no row. When the commit went through but its answer was lost (Postgres reports the transaction's own id as committed), the upload is stored and ingest reports it as stored, so a retry does not make a second copy; the objects are deleted when the transaction never got an id (the database was down at BEGIN, so nothing can have committed) or when Postgres reports that id as aborted, and when the database cannot say or the commit is still in flight, the objects are kept, the upload fails, and any left with no row are removed by the orphan sweep. Ingest never calls the slicer, so it returns before any slice runs ([#49](https://github.com/jonathanmcohen/platehouse/pull/49)).
- Bambu's own filament presets in the slicer (Jon, 2026-11-08: "I use mostly Bambu Filaments"): a slice now loads, for each filament, the printer's Bambu preset for its type where Orca 2.5.0 has one (PLA: Bambu PLA Basic, PETG: Bambu PETG HF, ABS: Bambu ABS, ASA: Bambu ASA, TPU: Bambu TPU 95A, kept in one table in apps/slicer/src/profiles.ts), else the printer's Generic preset, else the file's own filament. /v1/profiles lists that default once per printer and type, naming the printer, and a slice result's filamentProfiles names the preset loaded for each slot, or null where the file's own was kept. All 56 printers get Bambu's preset for all five types except 30 printer and type pairs Orca has no preset of either kind for (TPU on every 0.2 mm nozzle, ABS and ASA on the A1 mini and the A2L), which keep the file's own filament ([#55](https://github.com/jonathanmcohen/platehouse/pull/55)).
- Resumable uploads in apps/server/src/uploads: one tus 1.0.0 upload handler, mounted at /app/uploads for the UI behind its session and at /api/v1/uploads for the API behind a bearer token (registerTus takes each mount's auth hook, so a request the hook refuses stores nothing). An upload must give its size, at most 512 MiB, and its file name, and may name an existing model or a batch to combine; a missing name is refused with 400, an oversized or open-ended upload with 413 or 400, and a file type Platehouse does not take with 415, before any byte is sent. A client may send the file in chunks and resume after a dropped connection from where the server stopped, or send it all in one PATCH as curl does. Partial uploads live in TMP_DIR/uploads; a finished upload is queued for ingest under its own id, GET <prefix>/<id>/result reports pending, done (with the model and file) or failed (with ingest's own plain message, or, when the outcome cannot be confirmed, a note to check the library before sending the file again; never an internal error). The temp file is deleted after ingest whether it succeeds or fails, and the upload's small info file is kept, with a record of what the ingest did, until the sweep removes it a day later. During that day HEAD on the upload answers from that record, under the same lock tus uses, so it cannot catch the clean-up half done: after an ingest that stored the file, or one whose commit the database could not confirm, it answers finished (Upload-Offset equal to Upload-Length), so a client that retries after losing the last answer, or sends the same file again with its resume fingerprint kept, sends nothing and makes no second model; after an ingest that failed with nothing saved, it answers 410, so the same client starts a fresh upload. Nothing saved includes a database that was down when ingest started, and a failure while ingest was still writing its rows (a Postgres restart mid-insert, say), even when the database cannot then be asked how the transaction ended: no COMMIT was sent, so the stored objects are deleted. Only a failure at COMMIT whose outcome the database cannot report keeps them and counts as unconfirmed. HEAD carries no target, so the web client (Task 19) must put the target model or batch into its resume fingerprint, or drop the fingerprint once an upload succeeds; with tus-js-client's default settings, the same file dropped on another model within a day would resume the stored upload and store nothing there. An upload left untouched for 24 hours is deleted by an hourly sweep on the maintenance queue and never becomes a model. When tus answers a PATCH before reading its body (a wrong offset, too large), the answer goes out at once with Connection: close and the rest of the body is read off for up to 5 s before the connection closes, so a client still sending reads the answer rather than a reset. Responses carry no CORS headers and a relative Location, so no URL is taken from the request's Host header, and there is no DELETE on an upload ([#61](https://github.com/jonathanmcohen/platehouse/pull/61)).
- Inbox watcher in apps/server/src/inbox/watch.ts: a file placed in the inbox folder (INBOX_DIR) becomes a model of its own with no manual step. The folder is polled every 5 seconds rather than watched for events, which bind mounts and network copies drop, and a file is imported only once its size and modification time have stayed the same across polls for INBOX_SETTLE_SECONDS (15 by default), counted from when the watcher first saw them, read for each file as it is looked at so a slow import earlier in the same poll does not shorten the next file's wait, so a copy still running, or one that kept its source's old timestamp, is not taken early. Dotfiles, names ending in .part, .crdownload or .tmp, folders and symlinks are left alone. After ingest stores the file, the watcher checks that the recorded size and SHA-256 match the inbox copy and only then deletes it. A file goes to inbox/failed at once only for a reason that belongs to the file: ingest refuses it for its type or content (unsupported_type) or its target model (model_not_found), it is larger than the upload limit (MAX_UPLOAD_BYTES from the tus uploads, 512 MiB, read from its size before anything is uploaded), or its name is not valid UTF-8. It moves there as "name (2).ext" and so on when the name is taken and shortened when it would not fit, with name.reason.txt beside it holding one plain sentence; a file that changed during its import, or whose stored copy could not be confirmed, goes there too, with a reason saying a model was made. A damaged .3mf is not a failure: ingest stores it as a model with no plate data. Any other error leaves the file in place and stops the pass: ingest's ingest_failed (the save failed for a reason that is not the file's, such as a database or filesystem fault), storage_unavailable, a commit whose outcome is not known, and anything from the store, the database or elsewhere. The watcher then runs one quick check of the environment, each part given 5 seconds: a database query that also fails when the database is read-only or the role may not read or insert into files, then a model, a pending blob and a file row written in a transaction that is rolled back; and a bucket listing, then a small object put and deleted under a key outside models/, so the orphan sweep never sees it. If a check fails it is an outage: it is logged once when it starts, with the error, and once when it ends, and no file is tried, so none is uploaded again, until a check passes. The checks back off, 5 seconds after the first and doubling after each failed check up to 5 minutes, and start again at 5 seconds after a good pass. If both checks pass, the error counts against that file, and after 3 such failures in a row while the file is unchanged it moves to failed with a reason quoting the error and its cause; a change to the file starts its count again, and the other files keep importing in between. But when a second file fails the same way in the same pass with the checks passing (the same error code inside ingest's wrapper, or the same error name), the fault is taken to be one the checks cannot see, not the files': neither failure counts, the inbox is held, and the next try comes 5 seconds later, doubling to 5 minutes. Once the wait has reached 5 minutes (about 10 minutes of held tries), each try counts again, so two files that are each bad the same way still reach failed after 3 more tries 5 minutes apart. The hold is logged when it starts, when its tries start to count and when it ends, and it ends, and is forgotten, after any pass that leaves no hold armed, including one with no held file left to try, so a later fault always starts a hold of its own. The checks' writes are small and rolled back or deleted, so a fault can still miss them (a full Postgres disk fails an insert only when the table file has to grow, and a rolled-back write is not flushed); such a fault, one with a single file in the inbox, or one meeting files that settle apart, still moves the files it meets to failed after their tries. The watcher chooses each import's file row id itself and passes it to ingest, which gains an optional fileId for it: the id is shaped like a UUIDv7 and derived from the file's name, size, SHA-256 and the time it reached the inbox, so the same copy gets the same id after a restart. Before every import, not only after an outage, the watcher asks the files repository (files.findImported) for the row under that id. A row found, with its model live, means an earlier attempt's commit landed and only its answer was lost, in this process or in one before a restart, so the file is not imported a second time and its inbox copy is checked and deleted as after any import. Only an inbox attempt for this copy can write that id, so an upload of the same name and bytes through the web UI or the API, which gets a random id, never stands in for the inbox copy, and an import of the same file made before this copy reached the inbox does not count either. A row under the id whose model is in the trash or being purged (a purge deletes its stored bytes) is passed over, and the copy is imported under the next id. The arrival time is the file's ctime, taken when the watcher first sees its current size, modification time and inode and kept while they stay the same, so a chmod or an xattr write does not move it. The kept ctime lasts only as long as the process, so a metadata change made after a lost answer and before a restart can still let the file be imported twice. The lookup comes before the upload, so a database that cannot answer it stops the file before anything reaches the bucket. No file is retried in a loop: one that cannot be moved to failed, or whose inbox copy cannot be deleted after its import, stays put, is logged, and is not tried again until it changes. The blob store gains checkWrite, which puts and deletes one fixed object, checks/write-check, outside the blob layout; it is the only key outside models/ the app writes or deletes. On a bucket with versioning on it deletes the exact version it wrote, so the checks leave no old versions or delete markers behind for the retention period; a key that may not delete a version (s3:DeleteObjectVersion), or a provider that refuses it, gets a plain delete instead, which leaves the check's version and a delete marker until the retention period ends. The server's startup is not built yet, so nothing starts the watcher; the code that builds the server calls start() and stop() and passes files.get as storedFile, files.findImported as findImported and inboxProbes({ db, store }) as probes ([#59](https://github.com/jonathanmcohen/platehouse/pull/59)).

### Fixed

- Slicing gate harness, after the first Hades run: Orca 2.5.0 ships its presets only as binary .opc caches, so the image now takes the BBL profile JSON from Orca's source at the commit tag v2.5.0 points to, fetched by that commit and checked by git, and fails the build unless its version matches the .opc Orca ships; every image build check names what failed, and the checks match the real layout of the pinned artifacts; the scripts run when started through a symlinked path (#4); the README copies the tool with scp -rp, runs run.sh through bash, and copies the sample in one tar stream that keeps subfolder paths ([#5](https://github.com/jonathanmcohen/platehouse/pull/5)).
- Slicing gate image, after the second Hades run: Node would not start in the image because libatomic1 was missing, so both stages now install it and check Node's libraries before first running it; the gate user could not start Orca, because the extracted AppImage files kept modes only root could use (found by the new CI job), so both AppImage trees are now readable and executable for every user and the image checks that as the gate user; the README uses the ssh alias Hades exactly (OpenSSH matches it case-sensitively) and starts the long run detached, with its log and exit code in the scratch dir; the unused ORCA_SRC_TAG build arg is gone (#6) ([#7](https://github.com/jonathanmcohen/platehouse/pull/7)).
- Slicing gate, after the third Hades run: slicing a file on a printer other than its own failed with Orca code -3, because Orca 2.5.0 then loads the new printer's default process from resources/profiles/BBL/process_full/, which the AppImage does not ship, so the image now writes those presets, flattened from the pinned profile source, at build time without adding a BBL.json beside BBL.opc, and the build fails, naming the printer, if any printer would be left without its preset; every landrun call now ends landrun's flags with --, so OpenSCAD's -o is no longer read as a landrun flag; CI now slices a crafted two-plate cube saved for one printer on the other printers, with a control run that must reproduce the run 3 failure, and runs the landrun checks; a smoke check with long output no longer fails with SIGPIPE (#9); CI runs on pushes only to main and release branches, and editing check-libs.sh no longer re-downloads every artifact (#8); by Jon's decision on 2026-11-08, Orca codes -101 (G-code path conflicts) and -62 (filament temperatures too far apart) are legitimate refusals, reported with their reason, and no longer fail the gate or wait for a decision ([#11](https://github.com/jonathanmcohen/platehouse/pull/11)).
